# The pattern library, measured — 2026-09-15

Follows `planning/HANDOVER-pattern-library.md`. That handover asked for its own
conclusions to be re-litigated rather than built on, and the user's reason was
blunt: the earlier audit "was very bad, i kept correcting it". So every claim
below was re-derived here, and the corrections to the handover are stated first.

Everything is in the working tree; nothing is committed.

## What the handover got wrong

| claim | what the measurement says |
|---|---|
| "Path data uses only `M`, `C`, `c`, `s`" | **325 of 330** designs need more, and **143 use elliptical arcs**. The proposed "~60 lines for M/L/C/S" flattener would have silently mangled almost the whole library. |
| `Waves - 1` cut at rotation 0 gives "**1 solid**", the headline evidence for the `nocut` flag | That was an artifact of bug 1, which the same document reports. With bug 1 fixed, `decompose()` reports **6 parts** on its own — correctly. |
| "no visible seam defects at default settings", flagged as unverified | Now measured. **310 of 330** reproduce their design when repeated; 20 lose printable design to the box clip; 5 stroked designs of 107 have ribs that stop at the seam. |
| `seamOverflow` on 19 designs | Overlaps but does not match the 20 measured here. That test detected *geometry outside the box*; it never checked whether repetition puts that geometry back, which is the thing that matters. |

The tiering in `final.json` (`good`/`limited`/`drop`) is superseded. It was
derived from librsvg PNGs and morphological openings — it never ran the app.

## The four bugs

All four were reproduced from the code before being fixed.

1. **Unanchored simplify** (`pipeline.ts`). With `periodic` off, a rib crossing the
   box had its edge shaved 0.0033 mm and two repeats failed to merge. The early
   `cs.simplify(0.01)` exists to shrink the 3×3 neighbourhood, which only the
   periodic path builds and only it repairs, so it is now gated on `opts.periodic`.
2. **Thin-connection blindness** (`geom.worker.ts`). `decompose()` reports "1 part"
   identically for a 2 mm neck and an 0.008 mm one. `src/geom/thinConnection.ts`
   re-cuts the body with every pattern shape grown by half the minimum feature and
   counts again; a rise means the part only held together on ribbons no nozzle can
   lay down. Verified against the waves-1 box: with the sliver present the probe
   says 6 where `decompose()` says 1, **and it still says 1 for the 90° orientation
   that genuinely stays connected through the box rims** — which is why the check
   has to be 3D. A per-face 2D check would have condemned that one.
3. **Zero-tile hang** (`layout.ts`). Real, and the mechanism is
   `for (let j = -Infinity; j <= Infinity; j++)`, where `j++` never advances. The
   existing copy-count guard cannot catch it because the count comes out `NaN`.
   Now refused with a message. `generateTile` also no longer returns a null tile
   in silence.
4. **An imported SVG could not declare itself seamless** (`definition.ts`).
   `src/patterns/periodic.ts` measures whether the artwork's opposite edges match,
   at import. waves-1 is no longer forced into a kaleidoscope; a hand-drawn tile
   that does not line up still is.

Two detours worth recording, because both were wrong before they were right:

- The first periodicity detector compared thin strips inside each edge and called
  `honeycomb` broken. It is not: a slanted web boundary makes the bottom strip
  widen exactly where the top strip narrows, an O(slope·ε) error. Rewritten on
  edge spans — the method `repeat-audit.test.ts` already used — it agrees with all
  24 generators that declare themselves seamless.
- The first seam metric for the library rejected about half of it, because a
  checkerboard covers one edge and not the other and still tiles perfectly. Edge
  matching is the right test for a stroked rib and the wrong one for a filled
  design. See `measure-seams.ts`, which now measures both separately.

## The flattener

`src/patterns/svg/pathFlatten.ts` — DOM-free, full grammar (`M L H V C S Q T A Z`,
absolute and relative), so it runs inside the preview and geom workers where
`svgImport.ts` cannot. Validated two ways:

- `tests/path-flatten.test.ts`: shapes with closed-form areas — circles from arcs,
  a rotated ellipse, minified arc flags (`a10 10 0 11-20 0`, where `11` is two
  flags and not the number eleven), `S`/`T` reflection, malformed input.
- Against an independent renderer: all 223 fill-mode designs compared to the
  librsvg fill fractions in `analysis.json`. **Median difference 0.0004**, 95th
  percentile 0.005. The four outliers are all `seamOverflow` designs, where this
  clips to the box and that render did not.

Two things the arc code needed that are easy to get silently wrong: the flatness
test compares against `tol²`, not `tol` (the first version never reached the
tolerance it was asked for), and the four-point cubic approximation of a 90° arc
is accurate to 2.7e-4 of the radius, not 1e-5 — so the span is narrowed until the
requested tolerance is actually met.

## The library

`planning/pattern-library-2026-09-15/build-data.ts` → `src/patterns/library/data.json`
(330 designs, 1.1 MB) plus `NOTICE.md` with the MIT licence. Twelve colour layers
are rewritten at build time because the source fills with the nonzero rule while a
`Tile`'s polygons fill even-odd, which would void overlaps into holes.

`libraryGenerator` is one entry in the picker with the design as a parameter.
Stroked designs also emit the neighbouring copy of any rib that reaches an edge,
so clipping completes the rib instead of cutting it off; that alone took the
designs losing printable design from 26 to 20. Filled designs cannot be treated
that way — under even-odd a ring overlapping its own neighbour cancels.

Measured per design and carried into the tile's `notes`, which the app already
surfaces: `clipLoss`, `clipLossPct`, `ribBreak`, `ringParts`. Picking a design
that severs a closed box now says so at that moment — "falls into 6 loose pieces
(measured on a 50 mm box at a 50 mm repeat)" — instead of leaving the finding in
this folder.

**All 330 generate through the pipeline at 20/35/50/80 mm with zero failures.**
At a 50 mm repeat 6 collapse below the printability floor; at 20 mm, 28 do — which
is why "too fine" belongs in a warning at the chosen size and not in a reject list.

## Cutting the 50 mm box

All 330 cut through `fixtures/box-50.stl` as a through-cut on the closed ring of
four walls (margin 3, wall 1.6), counted both by `decompose()` and by the new
thin-connection probe. Zero errors.

| at a 50 mm repeat, of 326 cut | |
|---|---|
| stay one printable piece | **122** |
| visibly fall apart | 154 |
| look whole but hang on connections too thin to print | **50** |

**59 designs across the two repeat sizes pass `decompose()` and then fall apart
once sub-nozzle ribbons are discounted.** Every one of them would have shipped as
"one connected part" before bug 3 was fixed. That is the concrete value of that
fix, and it is much larger than the single case the handover found.

Against the handover's `nocut` flag, which was inferred from a 3×3 PNG of the
tile and meant to predict exactly this scenario:

| | |
|---|---|
| agreed it breaks | 86 |
| agreed it holds | 95 |
| flagged, but it holds | 27 |
| **cleared, but it breaks** | **118** |

55% agreement — and the 118 false clears are the dangerous direction. (The flag
is defined on the tile alone while this is one concrete body, margin and size, so
this measures how useful the flag is as a prediction, not whether its own
definition was computed correctly.)

Note what this does *not* say: falling apart as a through-cut on a **closed ring**
is not a defect of the design. All 330 remain usable as recess or emboss, and as a
cut on a bounded patch. That is why the result belongs in a warning at the chosen
mode and size rather than in a reject list.

## The picker

`src/app/PatternLibraryPicker.tsx`: a searchable thumbnail grid. The swatches are
SVG `<pattern>` elements built from the same stored path data, so 330 browsable
thumbnails cost no extra assets and no geometry work. Cards show the measured
flags; a "clean seams only" toggle hides the designs that lose something at the
seam.

Running it in the browser caught a layout bug that compiling did not: a
`@media (max-width: 640px)` rule reset `max-height: 100%`, and a percentage there
resolves against an auto-sized grid track rather than the viewport, so at a
569 × 287 viewport the modal rendered 925 px tall with the grid not scrolling —
the cards and the Close button were unreachable.

## Tests

170 pass, up from 147.

- `tests/tile-integrity.test.ts` — the four bugs, including a cut held together by
  0.01 mm ligatures that `decompose()` passes, and a cut that stays connected
  through the rims and must *not* be condemned.
- `tests/path-flatten.test.ts` — the flattener against closed-form geometry.
- `tests/pattern-library.test.ts` — every design generates, survives the pipeline,
  and matches its recorded measurements.

`seamless.test.ts` asserts a blanket property of every generator. Three library
designs genuinely do not have it, so the library is excluded from that sweep and
pinned by name in its own test instead — a fourth breaking still fails loudly.
This is the one deliberate loosening in this batch and it should be reviewed.

## Two mistakes of mine, for the record

- The first cut sweep leaked a manifold per cut and reached 4.2 GB. I reported
  that as a pattern blowing up the cut. It was the harness.
- After fixing the leak, 114 designs still errored — but each cuts fine alone.
  Manifold's WASM heap does not survive ~200 box-sized booleans in one process.
  The app only ever cuts once, so this is a property of sweeping. The sweep now
  runs in slices (`sweep-cut.ts <start> <count>`, merged by `merge-cuts.py`).

`planning/` is outside the TypeScript project, so `tsc` does not check these
scripts — a dangling reference in `sweep-cut.ts` cost one full sweep.
